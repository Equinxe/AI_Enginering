# Claude Code Hooks

---

# Purpose

`Adapters/git-hooks/` and `Adapters/github-actions/` enforce framework rules at commit time and at merge time. Both are late: by then the model has already run the command, written the file, or ended the session. Claude Code exposes **hooks** — shell commands it runs at fixed points of its own loop (session start, before and after a tool call, at stop) — and those points are early enough to refuse an action instead of rejecting its result.

These hooks make five rules mechanical for the one runtime that currently exposes the points to do it. A sixth hook, `dashboard-refresh.sh`, enforces no rule. It keeps the usage dashboard fresh, and is listed last because it is a convenience, not a control (Dashboard Refresh, below). A seventh, `context-alert.sh`, enforces no rule either: it reminds the Main Agent of the Handoff checklist when its context fills up, and blocks nothing (Context Alert, below). `context-statusline.sh` is not a hook but the `statusLine` command, installed the same way; it records how full the context is (Context Status Line, below):

# What They Are Not

- **Not a substitute for the git hooks or CI.** A model can be run without these hooks; a Pull Request cannot merge into `main` without the CI checks. These hooks remove the *first* opportunity to break a rule; `Adapters/git-hooks/` is a second local guardrail of the same kind, skipped by `--no-verify` or a `core.hooksPath` override — the escape hatches the runtime hook refuses; `Adapters/github-actions/`, behind branch protection, removes the last opportunity — the one a developer machine cannot skip, within the conditions `SECURITY.md` (Where the boundary is) states.
- **Not the framework's policy.** Every rule here is stated in a Standard or a Core document first; the hook is the executable form, and where they disagree the document wins (`Registry/README.md`, Authority). A rule that exists only in a hook is a rule the framework does not have — see `Adapters/README.md`, the Check Convention.
- **Not configurable around.** There is no environment variable that disables a block. (The switches in this directory turn off hooks that block nothing: `IAENG_USAGE_AUTO_REFRESH` turns off `dashboard-refresh.sh`, and `IAENG_CONTEXT_HOOKS` turns off `context-alert.sh` and the context status line.) The exception path is the one the Standards define: a human applies the action by hand after the Director decides, and the decision is recorded (`Standards/RISK_STANDARD.md`). A hook that can be told to look away is a suggestion.

**Not an adversary boundary.** The escape-hatch hook reads the command text. It models the shell's own constructions — quoting, ANSI-C `$'\x2d'`, brace expansion, command substitution, and `printf`'s backslash escapes (`git push origin $(printf '\x2b')…` and `$(printf '\x2d\x2dforce')` are decoded like the quoted forms, because printf's decoding is a deterministic shell mechanic). It cannot see a flag whose *value* is produced at runtime: a token an external program prints (`$(python -c …)`, `$(base64 -d …)`, `$(echo .. | tr . -)`), a flag a variable carries (`F=--force; git push $F`) or one split across two variables, `eval "$CMD"`, or a flag read from a file. Recovering those would mean evaluating the command, which is the thing the hook exists to happen *before*, and each is one keystroke from the next — so the honest line is "shell mechanics, yes; runtime values, no." It stops an escape hatch reached for by habit — which is the realistic failure — and the server side stops the rest: branch protection and the required CI checks, which run where a developer machine cannot skip them (within the conditions stated in `SECURITY.md`, Where the boundary is). The `pre-push` hook is a second local guardrail, not part of that boundary — it is skipped by `--no-verify` or a `core.hooksPath` override — the escape hatches the runtime hook refuses. Claiming more than that would be the false confidence this framework refuses elsewhere.
- **Not AI-agnostic.** They target Claude Code's hook contract (JSON on stdin; exit 0 allow, exit 2 block with stderr to the model; `stop_hook_active` on Stop). Another runtime with equivalent points gets its own directory under `Adapters/ai-runtimes/`; the Standards they enforce are the same. This is the same boundary `generate-agents.sh` draws: runtime-specific mechanics live in the Adapter, never in `Core/` or `Standards/`.
- **Not a Bash-command scanner.** `block-inline-suppression.sh` sees only Edit/Write/MultiEdit. A directive written through the Bash tool (`sed -i`, `tee`, `>`) is not inspected here, by design — the command text cannot be read for it without refusing every command that merely mentions a directive. A server-side advisory check, `Inline Suppression`, scans the Pull Request's added lines with the same pattern list (`Adapters/scripts/suppression-patterns.tsv`, which this hook also reads and fails closed without); it is not a required check, so a Pull Request can still merge past it until the Director promotes it.

# Design Rules

**Fail closed.** The two guard hooks, `block-escape-hatches.sh` and `block-inline-suppression.sh`, refuse input they cannot read — `jq` missing and the fallback extraction finding nothing, or a payload that is not a JSON object — with the reason, rather than allowing what they could not inspect. `session-start.sh`, `stop-gate.sh` and `post-edit-lint.sh` are not guards of that kind: they decide from git state or the file just written, and are reminders or feedback that do not refuse on payload content, so an unreadable payload does not make them block. A guard hook whose "nothing to check" outcome is allow (`block-inline-suppression.sh`) calls `iaeng_require_object` first, so a payload that is empty or not a JSON object is refused instead of being read as "no text"; a readable payload with no text to check is still allowed. The `lib.sh` helpers read with `jq` when present and with a sed extraction of the flat fields otherwise; the fallback is weaker than the `jq` path and can under-block. `block-inline-suppression.sh` matches the raw payload with its JSON escapes still encoded, so a directive containing a character JSON escapes (a tab, for example) and the rules anchored to a line start or end (a swallowed `except:` / `pass`, a skipped-test call at the start of a line) do not fire. Install `jq`; the decode fix is tracked as a separate Work Unit.

**Load from the hook's own directory.** `block-escape-hatches.sh`, `block-inline-suppression.sh`, `post-edit-lint.sh`, `session-start.sh` and `stop-gate.sh` find every file they load in their own directory, never in the working directory. This covers `lib.sh`, `strip-quotes.awk`, `context-alert.sh`, `../../../scripts/suppression-patterns.tsv` and the `tests/` exemption. The directory comes from `$0`, cut at its last `/` or `\`, when `$0` holds one; the environment cannot set `$0`. When `$0` is a bare name, it comes from `${BASH_SOURCE[0]}` instead. That happens when bash finds a hook through PATH, where `dirname "$0"` would be the working directory, so a cloned repository could plant any of these files there (issue #344). `BASH_SOURCE[0]` then holds the path bash found. That was run on bash 5.3.9, and read in the bash 3.2, 4.0 and 4.4 sources (`open_shell_script` in `shell.c`). `BASH_SOURCE` is not taken first because bash 5.3 imports it from the environment, so `BASH_SOURCE=<dir>/x` would load `<dir>/lib.sh` even through an absolute path (SEC-IAENG-400-01). The backslash counts because Git Bash's `dirname` reads it as a separator. Without it, a hook named `C:\…\hooks\stop-gate.sh` would load from the working directory. **The supported form is the installed one:** each hook is run by its absolute path (`"$CLAUDE_PROJECT_DIR/…/hooks/<hook>.sh"`). `bash <hook>.sh` found through PATH is not supported, because bash runs a file of that name in the working directory before it searches PATH, so a planted hook replaces the real one (SEC-IAENG-400-02). The rule above keeps only the helpers out of the working directory. `tests/own-dir.sh` runs each hook four ways. Three of them start from a planted directory: found through PATH, named by a path with backslashes only (Git Bash), and named by its absolute path with `BASH_SOURCE` set in the environment (where bash imports it). In those three, no planted file may be used. The fourth runs the hook found in its own directory, where nothing planted is reachable, so it checks only that the hook still does its job. When `lib.sh` cannot be loaded at all, each hook behaves as it did before, and the two guards then do not refuse (issue #361).

**Strip before matching.** `block-escape-hatches.sh` removes single-quoted strings, double-quoted strings, and heredoc bodies before applying its patterns. A commit message that *mentions* `--no-verify` is not a use of it, and this framework's own Standards mention every pattern the hook blocks. A sibling kit's first version blocked its own documentation commits for this reason.

**Name the exemption.** Documentation files are exempt from the suppression hook, by extension, in the script. `git stash list` and `git stash show` are exempt from the stash rule. `git push --delete` of a non-protected branch is allowed. Each exemption is a line a reviewer can read; none is a fall-through.

**Say what did not run.** `post-edit-lint.sh` reports "no linter ran for this file" rather than exiting silently, because silence reads as a pass.

# Purple Exercise #112 Corrections (29 Sep 2026)

Director-authorized static penetration test of `block-escape-hatches.sh`. Three findings against the `core.hooksPath` rule and the global-options prefix, closed under WU-IAENG-306; the other findings from the same exercise are separate Work Units and out of scope here.

- **Case-insensitivity.** git treats a config section and key case-insensitively — `core.hooksPath`, `core.HooksPath` and `CORE.HOOKSPATH` all disable the same hook — and the rule matched only the lowercase spelling. It now uses `check_key`, the same case-insensitive helper already used for `commit.gpgsign`.
- **`GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_KEY_<n>`.** These environment variables set git config for every git command that inherits them. `GIT_CONFIG_PARAMETERS=` is refused as a token, because its encoding is not decoded from the stripped command text. `GIT_CONFIG_KEY_<n>=` is refused when its value is empty, ends at a separator, or contains a `$` (a variable or substitution, whole or partial), so the key cannot be read from the command text. A fully literal key is judged by the case-insensitive `core.hooksPath` rule and by the list of control keys below (WU-IAENG-349); any other literal key, such as `safe.directory`, stays allowed.
- **Set through an assigning builtin, not just `NAME=` (WU-IAENG-316, PT2-07).** The variable can be set with no `NAME=` token: `printf -v`, `read`, `mapfile`/`readarray`, `export`/`readonly`/`declare`/`typeset`/`local`, `for NAME in`, `getopts`, `NAME+=` and `${NAME:=…}`. These are refused for `GIT_CONFIG_PARAMETERS` and for `GIT_CONFIG_KEY_<n>` when the name is the builtin's operand at command position, after any options and other names (`read -r a GIT_CONFIG_PARAMETERS`, `export A GIT_CONFIG_PARAMETERS`). Reading, removing and searching stay allowed: `printenv`, `echo "$GIT_CONFIG_PARAMETERS"`, `unset`, `grep`, `declare -p`, `export -p`, a commit message or heredoc that mentions the name. `export -n NAME` and `declare -n NAME` are allowed: `-n` removes the export attribute (or makes a reference) and sets no value. A bare `GIT_CONFIG_KEY_<n>` operand (`export GIT_CONFIG_KEY_0`, `read -r GIT_CONFIG_KEY_0`) is refused because its key cannot be read; `export GIT_CONFIG_KEY_0=…` carries the key in the text and is judged by the literal-key rule exactly as the inline form is (`=safe.directory` passes, `=$K` is refused). `GIT_CONFIG_VALUE_<n>` and `GIT_CONFIG_COUNT` are not refused in any form, as before; the key is what decides the risk. This is a speed bump: a name inside quotes (`export "GIT_CONFIG_PARAMETERS"`), a nameref (`declare -n r=GIT_CONFIG_PARAMETERS; r=…`), and a value built indirectly (`eval "$S"`, a script file) are still not seen. `read X < GIT_CONFIG_PARAMETERS` (a file of that name) is refused, a known false positive.
- **A variable index, and keys that turn off or redirect a control (WU-IAENG-349, issue #236; option B, Director, 20 Oct 2026).** The literal-key design stays, with two additions. First, a `GIT_CONFIG_KEY_` name whose index is a variable or a substitution (`GIT_CONFIG_KEY_$i=`, `GIT_CONFIG_KEY_${i}=`, `GIT_CONFIG_KEY_$(…)=`, the backtick form) is refused in every form: inline, `export`, `declare -x`, `typeset`, `readonly`, `local` and `env`. Those builtins receive the expanded word and set the variable, and the literal-index rules did not see it (`export GIT_CONFIG_KEY_$i=$K` was allowed). Second, `commit.gpgsign`, `include.*`, `includeIf.*`, `alias.*` and `core.fsmonitor` are refused, in any case spelling and whatever the value, when written literally as a `GIT_CONFIG_KEY_<n>` value in any of those forms, and as the key of a `git -c` or `--config-env` global option. One exception applies, through `git -c` only, when every such option in the command has the safe value: `commit.gpgsign` is allowed as the bare key or a literal true (`true`, `yes`, `on`, `1`), because that turns signing on; this keeps an older allow case. Any other value is refused: empty, `$`, or any other word. So is `--config-env`. As a `GIT_CONFIG_KEY_<n>` value, the key is always refused. The hook judges that value on de-quoted text, where a quoted or escaped `;`, `|`, `&`, `)` or space inside it reads as a token boundary. This is safe only because git refuses a non-boolean `commit.gpgsign`. `core.fsmonitor` therefore has no such exception (PR #258 review, F5): git runs a non-boolean value as the fsmonitor hook, so `-c core.fsmonitor=false\;/tmp/x.sh` would be judged `false` while git runs `/tmp/x.sh`. Every `-c core.fsmonitor` value is refused, `=false` included. A literal-false exception (issue #268) has to judge the raw value first: no quote, backslash, `$` or separator. Each listed key turns off signing, loads config from a file, redefines a command or runs a program, and none of that shows in the command text. A pair such as `GIT_CONFIG_KEY_0=commit.gpgsign GIT_CONFIG_VALUE_0=false` got past the signing rule because the value sits in a different variable. `core.hooksPath` is not repeated: the hooksPath rule already refuses it as a `GIT_CONFIG_KEY_<n>` value, and tests pin that. A key built in pieces is refused as unreadable, whatever the pieces are (PR #258 review, F1). This covers `GIT_CONFIG_KEY_0=core.hooks GIT_CONFIG_KEY_0+=Path` and every append (`+=`) to `GIT_CONFIG_KEY_<n>`, in any form and across statements, plus `${GIT_CONFIG_KEY_<n>:=…}` and `${…=…}`. An append to `GIT_CONFIG_VALUE_<n>` or `GIT_CONFIG_COUNT` stays allowed. Still allowed: any other literal key (issue #236's own `core.attributesFile`, `safe.directory`, `core.editor`), `GIT_CONFIG_COUNT` and `GIT_CONFIG_VALUE_<n>` in every form, a subcommand's own `-c` (`git show -c`), `git config alias.x …` (judged by the alias rule), `printenv`/`unset GIT_CONFIG_KEY_$i`, a prefix search such as `grep GIT_CONFIG_KEY_ dir`, and quoted mentions. A `$(…)` or backtick index is recognised only when the raw command shows the substitution right after the name, because the lexer prints it as separate words. As a result, a command that carries both a quoted mention with that shape and an unquoted prefix search is refused, a known false positive. So is a single-quoted search pattern with no whitespace, such as `grep 'GIT_CONFIG_KEY_$i=' dir`: the lexer keeps a quoted lone word as a command token by design, so put a space in the pattern or search for less of the name. So is an unquoted mention with the assignment shape, such as `echo GIT_CONFIG_KEY_0=alias.x`, as the earlier `GIT_CONFIG_KEY_<n>` rules already do: they match that shape anywhere outside quotes. Quoting alone is not enough when the quoted text is one word: `echo "GIT_CONFIG_KEY_0=alias.x"` is refused too, under the lone-word rule above. A quoted mention with whitespace passes, for example `echo "GIT_CONFIG_KEY_0=alias.x is refused"`. Not closed: `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and a config file that includes another reach the same keys through a file this hook never reads; that route is tracked in issue #245.
- **The global-options prefix (`G`) was too narrow.** It recognised `-C`, `-c`, `--git-dir=`, `--work-tree=`, `--no-pager` and `-P` — any OTHER real git global option ahead of the subcommand (`--no-replace-objects`, `--literal-pathspecs`, `-p`, `--no-optional-locks`, `--namespace=`, `--config-env=`, the space form of `--git-dir`) walked past every rule that anchors on `${G}<subcommand>`. `G` now matches every no-argument long option by shape, `-p`/`-P`, and the value-taking global options in both `=value` and `SPACE value` form.
- **The `core.hooksPath` read exemption was unanchored.** It matched a read flag and the key name anywhere in the command, in either order. It is now judged per segment (the command is split on `;`, `&`, `|` and newline): a segment is exempt only when it is a `git config` read (`--get`, `--get-all`, `--get-regexp`, `--list`, `-l`, `get`, `list`) that names `core.hooksPath`, with only a closed list of options (`--global`, `--system`, `--local`, `--worktree`, `--show-origin`, `--show-scope`, `--includes`, `--no-includes`, `--null`, `--name-only`, `-z`, and `--file`/`--blob`/`--type`/`--default` with a value) around the read keyword. Any other option leaves the segment un-exempted. A `-c`/`--config-env` naming hooksPath in the segment is never exempted, and a read in one segment does not exempt another segment. The legacy positional get `git config [--local|--global|--system|--worktree|--file X] core.hooksPath`, with nothing after the key, is also a read and is exempt on the same terms, but only for a plain command: when the raw command contains a quote (`'` or `"`), a backslash, a backtick, `$(`, a newline, a brace or comma (`core.hooks{P,}ath` expands to a write), or a glob character (`[ ] ? *`), the exemption is withheld and the command is refused as before. The lexer drops quoted text and the segment split hides what follows a newline, so `core.hooksPath ""` (an empty-value write), `co""re.hooksPath ""` (a key split by an empty quote pair) and a value on the next line after a backtick all strip down to a legacy read; a real read never needs those forms. This fails closed and has known false positives: `x=$(git config --local core.hooksPath)`, ``echo `git config core.hooksPath` ``, and any command that mentions the key beside a quote (a commit message) while also reading it. Use `--get` for those. `--add`, `--replace-all`, `--unset`, `--unset-all`, `set` and `-c core.hooksPath=…` stay refused.

`hooks/tests/escape-hatch-cases.tsv` carries the reproducing cases for all four corrections, each verified to fail against the pre-fix rule before the fix landed.

# Approval Label Guard

Rule: an agent never applies `control-change/approved` or `size/approved`. Only the Director does. `block-escape-hatches.sh` refuses a command that would apply either label, case-insensitively, and the block message says so.

Refused: `gh pr|issue edit --add-label` and `gh pr|issue create --label|-l` naming either label (also inside a comma list, in the `=` form, in a repeated flag, or in a quoted list with spaces such as `--add-label "help wanted,size/approved"`, which is read from a second lexing of the command in which quoted regions are kept as single words, so a label flag that is really a flag has its quoted value read, while the text of a `--body`, a `--title`, a commit message or a heredoc body is never read as a flag, a `gh` command or an alias; `$'...'` quoting is read the same way); the same commands with a repo flag before or inside the subcommand (`gh -R o/r pr edit`, `gh pr --repo=o/r edit`) or as `gh.exe`; `gh api` writes (a POST/PUT/PATCH, or any `-f`/`-F`/`--field`/`--raw-field`/`--input`) that name either label, where a GET or DELETE method exempts the command only if no POST/PUT/PATCH method is also present; a `gh api` write with `--input` to a `labels` endpoint or to an issue or pull request endpoint (`issues/N`, `pulls/N`, with or without `/labels`), because the file cannot be read and unread input is refused; `gh label edit --name|-n` renaming another label into either name; `gh label create` of either name; `gh label clone --force`, for the same reason as create; `gh alias set|import` when the command text names either label. The whole rule is skipped, with no process spawned, for a command with no `gh` in it.

Allowed on purpose: every read (`gh pr view --json labels`, `gh label list`, `gh pr list --label …`, `gh api` with no write); **removing** either label (`--remove-label`, `gh api -X DELETE`, `gh label delete`), because removal only withdraws an approval and can never grant one; editing the label's colour or description; mentioning the name in a commit message, a comment, `grep`, or `echo`, since quoted text is stripped as for every other rule.

Creating the label is refused although it applies nothing: the Director creates these two labels, so an agent has no legitimate reason to, and `gh label create --force` would otherwise let it redefine the label the guard workflow trusts.

**This is a speed bump, not a boundary.** The pull-request guard cannot tell an agent from the Director when both act under the same GitHub identity, so this hook only interrupts the agent that reaches for the label by habit or by mistake. The Bash tool can build the command indirectly and none of that is seen here: a variable, `eval`, a script written to disk, a label name produced by a command substitution, `curl` against the API, a GraphQL `addLabelsToLabelable` mutation (its query text is quoted and its label ids are opaque, so REST `--input` on the labels, issue and pull request endpoints is refused but a GraphQL body is not), a `gh` extension, a `gh alias` defined outside this session or without the label name in its text (including `gh alias import -` with the label in a heredoc body, or an alias file whose content is not in the command), a label name split across a quote boundary (`"size/app"roved`), and a `gh` invoked through a fully quoted path. The real control is the server-side check of who applied the label, which only works once the Director's identity and the agent's are separate. Until then, treat a block from this rule as the Director's line, not a bug to route around.

# SESSION_STATE Freshness

Measured on this repository on 24 September 2026: `.ia-engineering/SESSION_STATE.md`'s `_Last updated:` header read "9 September" while the last commit was 24 September — the body had been edited many times in between, the header never — and `session-start.sh` prints exactly that header into every new session's context, so a resumed conversation would have believed the state was fifteen days old. The same file had grown to 224 lines / ~36,000 characters, loaded unabridged on every resume. Nothing enforced `Templates/SESSION_STATE.md`'s "always update at session end": `stop-gate.sh` mentioned the file only when tracked changes were left uncommitted, and a clean tree gave no reminder at all. This section is the Director-approved (24 Sep) fix.

**The primary signal is the file's mtime, not the header.** The header is exactly what went stale in the incident above — a free-text line a session can forget to touch even while rewriting everything around it. The file's own last-modified time cannot lie the same way. Both hooks compare `.ia-engineering/SESSION_STATE.md`'s mtime (`date -r`) against `HEAD`'s commit time (`git log -1 --format=%ct`); `lib.sh`'s `iaeng_file_mtime` and `iaeng_head_commit_time` fail safe (empty output, non-zero exit) on any missing file, unsupported `date` flag, or git error, and every caller treats "could not compute" as "do not block, do not warn falsely" — never as "behind".

**`session-start.sh` — non-blocking, two warnings** (it is context injection; it has no compliance action to force, only information to surface):

1. **Behind the repository.** `.ia-engineering/SESSION_STATE.md`'s mtime is older than `HEAD`'s commit time. Reports how many commits landed since, via `git rev-list --count --since=@<mtime> HEAD`.
2. **Header not refreshed.** The `_Last updated:` header's date (parsed defensively out of its free-text line — an unparsable header is reported as unparsable, never silently skipped) is earlier than the file's mtime date. This is the specific failure the measurement above found: the body moved, the header did not.
There is no size warning. A third warning, for a file over 15,000 characters, was removed by WU-IAENG-368: the Director decided on 22 October 2026 that `SESSION_STATE.md` has no size limit — it is the agent's memory of what was done, the one file allowed to be very long and to keep its history (`Templates/SESSION_STATE.md`, No Size Limit). `tests/run.sh` holds a ~80,000-character fixture that must produce no size warning and must still be read to its last section.

**`stop-gate.sh` — blocking when behind, reminder when missing, fail-safe when the comparison itself cannot be trusted.** Checked only after the pre-existing uncommitted-tracked-changes gate has passed (a clean tree) — a dirty tree still blocks for that reason first, unchanged. When `.ia-engineering/SESSION_STATE.md` exists and its mtime is older than `HEAD`'s commit time, the hook **blocks the stop** (`exit 2`) and tells the agent to update it now — an absolute date in the header, "Where the Project Stands" and "Next Step" rewritten as a snapshot, not appended to as a log — then stop. This cannot loop: updating `SESSION_STATE.md` creates no commit (it is gitignored and refused by the pre-commit Adapter), so the next stop attempt sees a fresh mtime; the pre-existing `stop_hook_active` loop guard is checked first and unchanged, and still yields on the one continuation Claude Code grants after any Stop-hook block. When the file does **not** exist, the hook does not block forever waiting for one — a project that has never created it is a different condition from one whose file went stale, and blocking every no-state project on every stop would be the wrong response to a state that has nothing to be behind. It leaves a non-blocking reminder pointing at `Templates/SESSION_STATE.md` instead. And when `HEAD`'s commit is dated **after** the system clock — clock skew, or a deliberately future-dated commit — the hook does not compare mtime against it at all: see the correction below for why, and what it does instead.

Both behaviours are exercised by throwaway git repositories built under `mktemp -d` in `tests/run.sh`'s "SESSION_STATE freshness" section — filesystem state, not just a JSON payload, is what this rule reads.

**Portability and correctness corrections, found in review.** Warning 2's header parse first went through `date -d "24 September 2026"` — a GNU extension BSD/macOS date does not have, where the header-staleness check would have silently never fired. `lib.sh`'s `iaeng_ymd_from_header_date` builds `YYYY-MM-DD` out of the extracted day/month-name/year with a plain month-name table (`iaeng_month_num`) instead, so the check needs nothing beyond the `date -r` this file already established as portable.

Separately, and found in a second review pass: a future-dated `HEAD` commit used to make an otherwise-fresh `SESSION_STATE.md` compare as "behind" with no way to clear it. The first fix tried was `iaeng_cap_at_now`, clamping `HEAD`'s commit time at `min(HEAD_TS, now)` before every comparison — which *looked* fixed (a file touched in the same second as the check passed) but was not: "now" is read live on every invocation while the file's mtime stays fixed at whatever moment it was actually touched, so real time moving forward alone — with no edit made — silently re-opened the block a second later. Reproduced in review: `stop-gate.sh` returned `0` immediately after `touch`, then `2` one second later with nothing changed. The fix that replaced it treats a future `HEAD_TS` as its own condition rather than a value to clamp and keep comparing: when `HEAD`'s commit time is after `iaeng_now`, both hooks skip the mtime comparison entirely and report that the comparison itself cannot be trusted — `stop-gate.sh` warns and does **not** block (the same fail-safe branch as a missing mtime or a git error), and `session-start.sh` prints that warning in place of the "behind the repository" one. `stop-gate.sh`'s messages also print `HEAD`'s commit date next to the system clock for diagnosability. This is stable regardless of how much real time passes or how old the file's mtime looks, which `tests/run.sh` proves with a fixture whose mtime is a fixed date in 2020 under a `HEAD` dated tomorrow, rather than by sleeping in the test.

**Limit.** Both gates read the file's mtime, so `touch` satisfies them without the content changing; a future-dated `HEAD` is deliberately treated as unverifiable and does not block. This is accepted: the gate is a reminder for the session's own hand-off, not a control against it — nothing server-side depends on this gitignored file, and no hook can judge whether its content is current. A touch without a header edit is still reported by `session-start.sh`'s header-not-refreshed warning at the next session start, unless the header already carries that day's date.

# Dashboard Refresh

Director decision, 7 October 2026 (WU-IAENG-342): the usage dashboard (`Adapters/scripts/usage-dashboard.sh`, `Governance/DISPATCH_IN_PRACTICE.md` Measuring Usage) is kept fresh automatically at the end of each turn, and opened with `/dashboard` (`../skills/dashboard/`) with no rebuild to wait for.

`dashboard-refresh.sh` is the end-of-turn half. It calls the script's `--refresh-in-background` mode, whose contract is in the script's header under KEPT FRESH: returns at once, at most one refresh started per 60 seconds, one at a time, detached. The hook adds what a turn needs on top of that contract:

- **It cannot block, fail or speak.** Both of its output streams are `/dev/null` from its first line, and it exits 0 on every path. Its `settings.json` command adds `>/dev/null 2>&1 || true` and a 10-second `timeout`, so even a missing hook file (a framework pinned before it) costs nothing and says nothing. Whatever Claude Code would make of a `Stop` hook's output — a transcript line, or JSON read as a decision — there is none to read.
- **It does not wait.** It starts the script in the background and returns: on Windows Git Bash, the call that actually starts a refresh spends 1.5 to 2.7 seconds spawning it, and a turn should not pay that. Measured on Windows 11 from a parent reading the hook's stdout and stderr to EOF, as Claude Code does, on a loaded machine. Over 15 runs, the hook's settings command had a median of 601 ms, against 793 ms for the floor (the same command form, with a hook file that does not exist). Over 8 runs, `stop-gate.sh` had a median of 2,486 ms. Every run exited 0 with 0 bytes of output.
- **It leaves the stop gate's decision alone.** Claude Code runs the hooks of one event in parallel, so their order in `settings.json` sequences nothing. Independence is what protects the gate: this hook exits 0 with no output, which adds nothing, and `stop-gate.sh`'s exit 2 decides on its own. The refresh runs read-only git and writes only under the gitignored `.ia-engineering/usage/`, which the gate's `git status --untracked-files=no` never sees. When the gate blocks and the model continues, the next stop runs this hook again, and the script's debounce makes that a no-op.
- **Skipped silently** when the dashboard script is not beside it in the same framework checkout, or when the project opted out.

**Opting out.** The reliable switch is a file: create `.ia-engineering/usage-auto-refresh.off`. Commit it where the project's `.gitignore` allows (whole project), or keep it local (you only). The hook checks for it on every run, so it works wherever the hook runs. The other switch is `IAENG_USAGE_AUTO_REFRESH` set to `off` (or `0`, `false`, `no`, any case) in the shell, or in the `env` block of `.claude/settings.json` or `.claude/settings.local.json`. It reaches the hook only if the runtime passes that `env` to hooks, which reports say is not always so on Windows. That is unverified here, so do not rely on the variable there. Do not delete the hook's entry instead: `install-hooks.sh` adds missing framework entries back on its next run. `/dashboard` still works with the refresh off. It refreshes once when run, and says the automatic refresh is off.

**The `/dashboard` skill** (`../skills/dashboard/`) is the other half. Its `SKILL.md` holds only the instructions the model follows on `/dashboard`, because the whole body is added to the conversation each time; the reasons are kept here.
- It is a Claude Code wrapper around `usage-dashboard.sh --open --no-wait`. What the page shows and what it decides are in `Governance/DISPATCH_IN_PRACTICE.md`, Measuring Usage; the skill adds nothing to either.
- It is user-invoked only (`disable-model-invocation: true`): opening a browser window is the user's call, not the model's.
- Its `allowed-tools` rule is an exact match on the one command it runs. That is why the command is relative and must be run as written: a `cd` or prefix would no longer match and would ask for permission. A session whose working directory has moved off the project root is told so in one line.
- A project's first `/dashboard` builds the page in the foreground, so it waits; every later one opens at once. The 600000 ms Bash timeout covers that build: cold builds were measured at 9 s for an adopter and 57-90 s for the framework itself on a loaded Windows machine, which leaves a margin of more than six times. The build stays in the foreground on purpose. Its errors then reach the user in the launcher's line, rather than in a background log nobody opens.
- Its launcher `open-dashboard.sh` finds the project from where it is installed. It takes the dashboard script from `$IAENG_FRAMEWORK`, then the project's `ia-engineering/`, then the project root, so an adopter's pinned framework is never shadowed by a root-level `Adapters/scripts/` of its own.
- Its one line says what actually happened, worded from what `usage-dashboard.sh` printed:
  - "a refresh is running now", when the page opened as it was and a refresh started behind it;
  - "a refresh already running will update it";
  - "built just now", for a first page built in the foreground, when no refresh is started.
  The Stop hook is credited only when `.claude/settings.json` or `settings.local.json` registers `dashboard-refresh.sh`; otherwise the line says the hook is not installed. An opt-out is named. When the browser could not be opened, the line says "no browser could be opened; open it yourself" and gives the path, since the script reports that as a note and still exits 0. On Windows, `explorer.exe` returns no usable status, so a failed open there cannot be detected or reported.

**Not on `SubagentStop`.** Considered and declined. The main agent's `Stop` already fires after every subagent result: at the end of the turn that waited for a foreground subagent, and at the end of the turn a background subagent's completion notification starts. `SubagentStop` would add a bash start (133 ms at best, 601 ms median on the loaded machine above) to every subagent's completion, multiplied in a parallel fan-out, for refreshes the 60-second debounce would mostly drop. The page would gain freshness only inside a long foreground orchestration, and it catches up when that turn ends.

# Context Status Line

Compaction plan of 23 October 2026, step B (issue #304, WU-IAENG-379). Claude Code gives `context_window.used_percentage` to one place only: the stdin of the `statusLine` command ([statusline docs](https://code.claude.com/docs/en/statusline.md)). `context-statusline.sh` is that command. It writes the percentage where the context alert reads it, and otherwise shows the status line the user already had. Director decision of 23 October 2026: it is **on by default** through `install-hooks.sh`, and the Director types no command.

**The file.** `${TMPDIR:-/tmp}/iaeng-ctx-<uid>/<session_id>.pct` holds the floor of the percentage and a newline, such as `42`. TMPDIR counts only when it is an absolute path with no `.` or `..` component, with either separator (`C:\a\..\b` is refused as `/a/../b` is), else `/tmp`. That rule lives once, in `context-dir.sh`, which this script and the context alert both source, so the writer and the reader cannot name different directories (issue #340). `IAENG_CTX_TEST_FALLBACK` takes the place of `/tmp` in that rule. It is for the hook tests only, so that no test writes into your real directory (issue #345). The same rule judges it, and a value the rule refuses leaves `/tmp`. The session id must match `[A-Za-z0-9][A-Za-z0-9_-]{0,127}`: no dot and no separator, so no path can be built from it. The directory is created mode 0700, and it is used only when it is a directory, not a symbolic link, owned by the user, and writable by no one else. On Windows, Git Bash cannot set the mode, but the profile's `TEMP` belongs to the user. The file is written mode 0600 whatever the caller's umask (the umask is set in a subshell around that one write, so it never reaches your own command), under a new name with noclobber, then renamed over `<session_id>.pct`, so a reader sees either the old value or the new one. A rename replaces a symbolic link without following it. A final name that is a link, or anything but a regular file, is not written. A `find` that fails is not read as "no one else can write": the write is skipped. A reader such as the context alert hook takes the same path from `context-dir.sh` and makes the same checks. The percentage comes from the stdin JSON only, never from a transcript. **Cleanup is the writer's job** (Main Agent decision of 26 October 2026). At most once an hour, the script deletes the `*.pct` and `*.alert` files older than 24 hours in its own directory. It also deletes the `.*.tmp` files older than 24 hours there (issue #345). Those are its own temporary files and the context alert's, left behind when a process is killed between its write and its rename, as a status line run under a timeout can be. It deletes only regular files the user owns, at the top of the directory, and `find -type f` never matches or follows a link. The hour is kept as an epoch in `.last-clean`, read and written with bash builtins, so a run that does not clean starts no process. A bash older than 4.2, such as macOS's stock 3.2, has no builtin clock, and there nothing is deleted. A marker that is a link, or not a regular file, stops the cleanup. A reader such as the context alert never deletes anything. Bash itself may also create a short-lived file of its own in TMPDIR for the stdin it hands your command, mode 0600, which it deletes.

**Fail-open.** It exits 0 on every path but the switched-off one (Turning it off, below) and prints nothing on stderr. It always prints a line, because Claude Code shows nothing for an empty output or a non-zero exit. Empty stdin, bad JSON, a hostile session id, a planted link or a read-only TMP all get a line, and nothing else happens. Without `jq`, the three fields are read by pattern.

**Your own status line is kept.** A `statusLine` in the project's `.claude/settings.json` wins over the one in your `~/.claude/settings.json` ([settings precedence](https://code.claude.com/docs/en/settings.md#settings-precedence)), so installing this one would hide yours. The script therefore runs yours itself, with the same stdin, and prints its output unchanged, colours included. It reads yours from `${CLAUDE_CONFIG_DIR:-~/.claude}/settings.json`: a `command` runs under bash, the exec form (`args`) as its argv, and `"shell": "powershell"` under `powershell -Command`. The file is read with `jq`, or without `jq` by pattern. The pattern reading handles a flat `statusLine` object, as in Claude Code's own examples, and decodes its JSON escapes except `\u`. A command that holds a `\u` escape is not run without `jq`. When the project's own `settings.json` already had a `statusLine`, `install-hooks.sh` does not replace it. It wraps its command: the framework's command, then `--chain` and the project's command in single quotes. The statusLine's other fields, such as `padding`, are kept, and the exec form is folded into the command. When the statusLine already runs this script from an earlier framework path, that path is updated in place and its `--chain` is kept. Your output is used when your command exits 0 within `IAENG_CTX_CHAIN_TIMEOUT` seconds (default 10, where `timeout` exists) and prints something. Otherwise the script prints its own line, `[<model>] ctx <n>% | 5h <n>%`. On Git Bash under heavy load, the timeout's signal can arrive late, and your command, or a child process it started, holds the line until it ends. In this Work Unit's tests that happened with twelve suites running at once, and never in a run on its own. Linux enforces the timeout, and CI checks it there. Your command would have held the status line just as long without this script. The `.pct` is written before your command runs, and your command keeps the umask Claude Code gave the script. A command that names this script is not chained, so it never loops. A `--chain` that names it, an earlier path the installer has not updated yet, falls back to your user statusLine, so neither line is lost. The `padding` and `refreshInterval` of the statusLine in your user file are not carried over. The wrapped project statusLine keeps its own.

**What it cannot chain.** A project `statusLine` that runs under `"shell": "powershell"` is kept as it is, and the installer says so: on stderr, and as a `statusline near-miss` record under `--check`. The context % is then not recorded. A `statusLine` in `.claude/settings.local.json` wins over the project's for that developer. The installer reports it (`statusline shadowed`) and never changes it. `"disableAllHooks": true` switches off the status line too, as the installer's warning already says.

**Its own line.** Every field it prints from the JSON goes through the framework's record sanitiser rule (the `flat()` block it shares byte for byte with the installers), so no control character, C0 or C1, reaches the terminal. Colour appears only when `NO_COLOR` is unset or empty: the ctx part turns yellow at or above `IAENG_CTX_ALERT_PCT` when that variable is set.

**Turning it off.** Create `.ia-engineering/context-hooks.off` in the project, or set `IAENG_CONTEXT_HOOKS` to `off` (or `0`, `false`, `no`). Then nothing of the script's own stays (AC5). It writes no file and creates no directory, and your status line command replaces the script's process, with the same stdin. Its output and exit status are therefore exactly what Claude Code showed before the install, and with no status line of your own nothing is printed, as before. The context alert of step C is to honour the same switch. Removing the `statusLine` key would not last, because the next `install-hooks.sh` run adds it back, as it does for a hook entry.

**Cost.** One `jq` call for the fields, a second one when your user file is read, and a `find` and a `mv` for the write. Measured on the Windows 11 machine of the Dashboard Refresh measurements, the script costs a few hundred milliseconds on top of your own status line command. Claude Code debounces status line updates at 300 ms and cancels a run still in flight when the next one starts.

The tests are `tests/context-statusline.sh`, run by `tests/run.sh`.

# Context Alert

The compaction plan of 23 October 2026 (issue #304, WU-C; WU-IAENG-380). A compaction that comes while the Main Agent holds state nowhere else loses that state. The alert asks for the Handoff before that happens, while the session still has room to write it. It is on by default, through `install-hooks.sh`, and the Director types nothing.

**What it says, and when.** Two steps, each said once per crossing:

- At `IAENG_CTX_ALERT_PCT` (default **60 %**, the Director's provisional default of 23 October 2026, to be reviewed at the D+14 measurement): head for the Handoff without stopping the work in hand. Finish the Work Unit in progress and start no other. Dispatch no new Employee for any other work; continuing one already dispatched, or dispatching one the Work Unit in progress still needs (its reviewers), is allowed. Then run the Handoff to a New Conversation checklist of `Templates/SESSION_STATE.md`, items 1 to 6, say so in one line and carry on.
- At the last call, `IAENG_CTX_LAST_CALL_PCT` (default: the alert + 10, so **70 %**): write the Handoff now, even with the Work Unit unfinished, recording where it stands, then resume the Work Unit.

Why +10: in `Governance/CONTEXT_COMPACTION_MEASUREMENT.md`, auto-compaction ran at a median of 96.8 % of the 1M window and never below 84.8 %, and ordinary growth is about 3 points per 20 calls. 70 % leaves about 15 points before the lowest compaction seen, and the 10 points between the two steps are about 64 calls, room for most Work Units to close. A reading past both steps at once gets the last call alone. A reading below the alert, after a compaction or a `/clear`, re-arms both.

**How it works.** The message is `additionalContext` on `UserPromptSubmit` (beside the prompt) and on `PostToolBatch` (after a batch of tool calls, before the next model call), so a long stretch of work with no prompt is covered too. Both are documented events ([hooks reference](https://code.claude.com/docs/en/hooks.md)). A payload with a non-empty `agent_id` is a subagent's and is ignored: only the Main Agent is told. `agent_type` alone is not a subagent, since the main thread carries it under `claude --agent`.

The percentage is read only from `${TMPDIR:-/tmp}/iaeng-ctx-<uid>/<session_id>.pct`, which `context-statusline.sh` (WU-IAENG-379) writes, never from the transcript. The directory is named by `context-dir.sh`, the one rule both hooks source (issue #340). It is believed only when the directory and the file are not links, are owned by you, and cannot be written by group or others, and when the file holds one whole number from 0 to 100 and nothing else (4 bytes at most). Without the file — no status line installed, another status line in `settings.local.json`, a session that has not rendered one yet — the hook is silent. What was said is kept beside it, in `<session_id>.alert`, never in the project. The record is written to a new name and renamed into place, never through a link. The message is printed only when the record was written, so an alert is never repeated on every prompt. The `.pct` must not be group- or world-writable: the writer creates it `0600` whatever the umask (#321). **On Windows** (Git Bash on NTFS) the mode bits are not kept and every file of yours passes the owner test, so the group/other and owner rules are always met there; the boundary is the per-user `%TEMP%` ACL, as for the writer.

**Only this session's files.** The hook reads `<session_id>.pct` and `<session_id>.alert` of the session in the payload and nothing else in the directory. Another session's files are never read, judged or removed: a session that ended after crossing a step costs the others nothing, and two sessions with different thresholds cannot re-arm each other. Removing the files of ended sessions is the writer's job (#321).

**Its cost.** `PostToolBatch` runs after every batch of tool calls, and on Windows every process costs: the `bash` running the hook is the floor. So the hook reads the payload's first 4 KiB and this session's two files with shell builtins alone, and exits there, starting no process, when this session has no step left to hear. It drops a payload whose head names an `agent_id` (an Employee's batch) the same way. It reads the rest of the payload and starts `jq` only when there is something to say or a record to re-arm. A test runs the hook with every command it can start replaced by a shim that leaves a mark, and checks that none is started in those cases.

**The SessionStart warning.** `session-start.sh` runs the hook with `--session-start` and prints what it says among its own lines, so the template keeps one `SessionStart` group (the framework's earlier-matcher update of WU-IAENG-373 relies on that). The hook then estimates where auto-compaction may run, as a percentage of the window the status line measures (`TROUBLESHOOTING.md`, section A, item 5). The median point is `CLAUDE_CODE_AUTO_COMPACT_WINDOW` over an assumed 1,000,000-token window (96 % when it is unset), times `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` / 100 when that is set. The warning uses the floor, 12 points lower: in `Governance/CONTEXT_COMPACTION_MEASUREMENT.md` the lowest compaction (848,341 tokens) came about 120,000 tokens under the median one (968,011), because a large turn can trigger it from the last reading. So with the default window the floor is 84 %. When the alert is at or above the floor, it says so and asks the Main Agent to tell the Director. When only the last call is, it says that only the first alert is sure to come in time. It reads only the environment: a window set with `/autocompact` or `autoCompactWindow` is not seen. With `DISABLE_AUTO_COMPACT` or `DISABLE_COMPACT` set, there is nothing to compare and nothing is said. An `IAENG_CTX_ALERT_PCT` that is not a whole number from 1 to 100 is also said there, and the default is used.

**Settings.** `IAENG_CTX_ALERT_PCT` and `IAENG_CTX_LAST_CALL_PCT` (a whole number above the alert, at most 100) are read from the hook's environment: the shell that started `claude`, or the `env` block of a settings file, subject to the same caveat on Windows as `IAENG_USAGE_AUTO_REFRESH` above. **Opting out:** the file `.ia-engineering/context-hooks.off` in the project, or `IAENG_CONTEXT_HOOKS` set to `off` (or `0`, `false`, `no`, any case); both also turn off the status line's file. Do not delete the hook entries: `install-hooks.sh` adds them back.

**Not done here, on purpose.** It never blocks, never holds a compaction (that is WU-E, deferred by the Director on 23 October 2026), never writes `SESSION_STATE.md` itself and never reads the transcript.

# Installation

From the project root, with the framework imported at `ia-engineering/` (or from the framework repository itself):

```bash
./ia-engineering/Adapters/ai-runtimes/claude-code/install-hooks.sh
./ia-engineering/Adapters/ai-runtimes/claude-code/install-skills.sh   # /dashboard (and /create-project in a project)
```

**Behaviour change in WU-IAENG-342.** Before it, `install-hooks.sh` refused an existing `settings.json` that differed from the template, with exit 1. Now it merges into it and exits 0. One consequence for adopters: a framework hook entry a project deleted comes back on the next run. For the guards this is intended: they are not configurable around. To turn off the dashboard refresh, use its own switch (`.ia-engineering/usage-auto-refresh.off`, see Opting out above), not a deleted entry.

This writes `.claude/settings.json` from `settings.example.json`, substituting the framework's path. It never overwrites an existing `settings.json`; it **merges** into it instead. Each framework hook entry the file does not yet have is appended to its event. An entry counts as present **only exactly**: a group under the same event, with the same matcher, holding an entry equal to the template's in every field — its command, its `type`, its `timeout`, any other — in any key order. Only the spelling of the project directory in the command is normalised (`${CLAUDE_PROJECT_DIR}`, `/./`). So a re-run of an installed file adds nothing. An entry that only *names* a framework hook script — under a matcher that never fires, with `|| true` cancelling its block, inside an `echo`, a project's own script of the same name under another `hooks/` folder such as `scripts/hooks/stop-gate.sh`, or the exact command with `"timeout": 1`, after which the runtime carries on as if the guard had not blocked — is not counted as the guard (PR #239 security review, F1, and code review; issue #241). The framework's entry is appended beside it, since a hook run twice is harmless, and the installer prints the other command as a near miss, for the project to check it is not a weakened copy; when its command is the template's, the near miss names the fields that differ (`differs in: timeout`).

**The framework's own earlier entry is updated in place (WU-IAENG-373).** When a framework version changes the matcher of one of its entries, appending the current entry beside the earlier one would leave two groups that both fire on the events they share. The hooks reference says a handler defined in several settings *files* runs once; it says nothing of two groups in one file. So the installer knows the framework's earlier matchers, today one: SessionStart `startup|resume|compact`, which became `startup|resume|clear|compact` so that `/clear` gets the read-first context. A group under that event whose matcher is exactly the earlier one and which holds exactly the template's entries — nothing else in the group, nothing else on it — has its matcher changed and nothing more, and the installer prints it as `updated:`. Any other group is the project's and is never rewritten: the earlier matcher with another field (a `timeout`, a hook of the project's own in the same group, a key of the group's own such as `$comment`), or the earlier group beside the current one already there, is a near miss as above. `--check` reports such an entry `absent`, naming the update a run makes, never as a near miss.

**`"disableAllHooks": true`** in `.claude/settings.json` or `.claude/settings.local.json` makes Claude Code run none of the hooks, the guards included. The installer never changes it, since it is the project's setting, but says so on every run until it is removed: on stderr, and as a `WARNING:` line in its report (issue #241).

**Line endings.** Each installer adds its line to the project's `.gitattributes` when it is missing: `/.claude/settings.json text eol=lf` (`install-hooks.sh`) and `/.claude/skills/** text eol=lf` (`install-skills.sh`, whose launchers are bash scripts). Without them a clone with `core.autocrlf=true` checks those files out CRLF, unlike the framework's own copies (issue #242). The line is found whether `.gitattributes` is LF or CRLF, so a re-run adds nothing; nothing else in the file is touched. `Adapters/scripts/install.sh` writes the same two lines among its own, and each script finds the line the other wrote. Commit `.gitattributes` with the files. Every entry already in the file is kept unchanged: the project's own hooks, `env`, `permissions`, `$comment`. The file is rewritten by `jq`, so its formatting is normalised. The installer lists what it added and what it found present, nothing else. Without `jq`, when the file is not one JSON object, or when it is a symbolic link (a merge would replace the link with a file), nothing is written: `--print` shows the file to merge by hand, and `--force` replaces the file after you have reviewed what else it contained. This is how a project picks up a hook added in a newer framework version, such as `dashboard-refresh.sh`. Restart the session for the hooks to load.

`.claude/settings.json` is **committed**: Claude Code reads its hook configuration from the repository, so every session on every clone runs these hooks without a per-clone install step — the property git hooks cannot have. The corollary is that this file is reviewed like code, because it decides what the model is allowed to do.

`jq` is recommended. Without it the hooks still run, on the fallback described above.

# Verifying

There is a test suite, and it is the control:

```bash
./Adapters/ai-runtimes/claude-code/hooks/tests/run.sh          # the whole suite, tests/dashboard.sh included (CI reports the total)
./Adapters/ai-runtimes/claude-code/hooks/tests/run.sh --verbose
./Adapters/ai-runtimes/claude-code/hooks/tests/dashboard.sh    # 114 checks: the dashboard refresh, installers and /dashboard alone
./Adapters/ai-runtimes/claude-code/hooks/tests/context-alert.sh  # the context alert alone (counted by run.sh too)
./Adapters/ai-runtimes/claude-code/hooks/tests/context-statusline.sh   # the context statusLine and its install, alone
```

`tests/context-statusline.sh` runs the statusLine on real files in a scratch `TMPDIR` and `HOME`. Its inputs are empty stdin, bad JSON, ESC, CR and C1 in the fields, `../` and other malformed session ids, a planted symbolic link (the directory and the file), a directory others can write in, a read-only, missing, relative or file `TMPDIR`, and no `jq`. Each must exit 0 with a non-empty line and nothing on stderr, and the `.pct` must be written only where it should be. It also chains a user statusLine (bash, exec form, failing, silent, slow, this script itself) and tests the two off switches. Then it runs `install-hooks.sh`: a fresh install, an adopter's statusLine wrapped (its padding kept, an apostrophe intact, the exec form folded, and a re-run that wraps nothing twice), a PowerShell one kept, and a `settings.local.json` one reported. The installed command is run as Claude Code runs it, with `bash -c`. A check the platform cannot run is printed as `n/a` with its reason and is not counted as a pass: a symbolic link Git Bash may not create, or a mode Windows does not enforce. CI runs those checks on Linux.

`tests/context-alert.sh` ends with the writer and the reader run together (issue #340). It tries each `TMPDIR` form: unset, normal, with a trailing slash, with `.` or `..` and forward slashes, `C:\x\..\y` and `C:\x\.\y` with backslashes, `C:/x/./y`, relative, a regular file, and missing. On Windows it adds the real backslash and drive forms. For each form, the real statusLine records 90 %, then the real alert runs under the same environment. The test checks that the `.pct` lands where a hand-written rule says it should, and that the alert finds it. Otherwise, both must refuse alike, with no file anywhere. A copy of `context-dir.sh` without its backslash handling fails it.

Neither test touches your real context directory (issue #345). Every case runs with a scratch `TMPDIR`, and with `IAENG_CTX_TEST_FALLBACK` set to a scratch directory, so a `TMPDIR` the rule refuses falls back there and not to `/tmp`. That `/tmp` is the fallback by default is checked by naming the directory, which writes nothing. Both tests end by checking that `/tmp/iaeng-ctx-<uid>`, and the one under the `TMPDIR` they were given, gained or changed no file (`tests/real-ctx-dir.sh`). Your own sessions keep writing there while the tests run, so names that start with a session UUID, and `.last-clean`, are left out of that check. A deletion is not checked: only files older than 24 hours are ever deleted there, and your sessions delete those too.

It feeds `tests/escape-hatch-cases.tsv` to the escape-hatch hook (one `block`/`allow` case per line), checks that the guard hooks fail closed on unreadable input and that each hook ignores tool calls that are not its own, and runs `tests/lexer-cases.tsv` through `strip-quotes.awk` directly. The CI job **Hook Tests** runs it on every Pull Request.

`tests/dashboard.sh` runs every call of `dashboard-refresh.sh` under a command substitution that receives both of its streams. That substitution ends only when every holder of either pipe has closed it, so output, a non-zero exit, or a child left holding a pipe each fails a check. It uses a fake dashboard script that prints on both streams, leaves a child running and exits 3, and then the real script for a project that does not exist, is not a git work tree, or keeps a cache git does not ignore. It also runs the `settings.json` command as Claude Code does (`bash -c`), with and without the hook file, checks the `install-hooks.sh` merge (adds once, keeps a project's own entries, never duplicates, compares every field of an entry, names `disableAllHooks`, refuses a malformed file untouched), and checks `install-skills.sh`, `SKILL.md` and the `/dashboard` launcher. Last, it commits a project after both installers and clones it with `core.autocrlf=true`: the installed files come out LF, while a file no rule covers comes out CRLF, the control that shows the clone converts at all. Against the installers before issue #242 and #241 were fixed, 19 of its checks fail. A run of it against a hook stripped of its output redirect and its background start failed 9 checks; restored, it passes.

It exists because shellcheck proves the hooks are valid shell and the validator proves the documents around them agree, and neither can say whether `git push --force` is actually refused. Feeding payloads by hand found seven real defects — a trailing `;`, a global option before the subcommand (`git -C . push --force`), the short `-n` form of `--no-verify`, a quoted lone flag (`git commit "--no-verify"`), a line continuation, the other argument order of a protected-branch deletion — and one false positive that refused `grep -rn -- --no-verify Standards/`, which is precisely how a hook teaches people to work around it. Adding a case is adding a line to a `.tsv`.

Cases live in data files, not in the runner, for two reasons: a corpus full of escape hatches typed into a terminal is refused by the hook under test, and a case containing a command substitution is then data that no shell ever parses.

Each hook can also be run by hand with a payload on stdin; exit code and stderr are the contract:

```bash
printf '{"tool_name":"Bash","tool_input":{"command":"git push --force"}}' \
  | bash Adapters/ai-runtimes/claude-code/hooks/block-escape-hatches.sh; echo "rc=$?"     # rc=2

jq -n --arg c 'git commit -m "docs: never use --no-verify"' '{tool_name:"Bash",tool_input:{command:$c}}' \
  | bash Adapters/ai-runtimes/claude-code/hooks/block-escape-hatches.sh; echo "rc=$?"     # rc=0 — the flag is only inside quoted text, which the lexer strips

printf '{"tool_name":"Write","tool_input":{"file_path":"a.py","content":"x = 1  # noqa"}}' \
  | bash Adapters/ai-runtimes/claude-code/hooks/block-inline-suppression.sh; echo "rc=$?" # rc=2

printf '{"stop_hook_active":true}' \
  | bash Adapters/ai-runtimes/claude-code/hooks/stop-gate.sh; echo "rc=$?"                # rc=0 — loop guard
```

The Shellcheck Adapters CI job covers this directory with `shellcheck -x -P SCRIPTDIR …` — `-x` follows `source`, `-P SCRIPTDIR` resolves each hook's `# shellcheck source=lib.sh` directive relative to the hook's own directory. Run the same command locally before pushing; a portable ShellCheck binary is enough. The quote-stripping lexer lives in `strip-quotes.awk` rather than in a quoted string inside the hook, so no shell quoting applies to it and nothing in it needs a directive.
