# oh-my-claudecode (OMC) Adapter

---

# Purpose

oh-my-claudecode is a multi-agent orchestration layer that runs on top of Claude Code: named agents (`executor`, `architect`, `critic`, `verifier`, `code-reviewer`, …), skills that launch multi-agent modes (`autopilot`, `ultrawork`, `ralph`, `team`, `ralplan`), and a local state directory (`.omc/`). Several IA Engineering adopters run it. This document says how the framework's concepts map onto it, what the mapping does **not** cover, and where the framework's rules bind regardless of what the runtime offers.

It is a **transport mapping**, not an endorsement and not a dependency. `Core/AI_MANIFEST.md` Principle X holds: no Core document, Standard, Employee, or Workflow names OMC. This file is the only place the mapping lives, and a project that does not use OMC never reads it.

**Status of the facts here.** The OMC behaviours described are taken from OMC's own installed instructions (the `oh-my-claudecode` global `CLAUDE.md` and its `omc-reference` skill) as observed on adopters' machines at the time of writing. They were **not** independently tested in this repository's CI — there is nothing here that runs OMC — so every mapping below is a statement about how the two are *intended* to line up, to be verified on the adopting project and corrected here when wrong (`Governance/CONTRIBUTING.md`, Section 7).

# The Mapping

| IA Engineering | OMC | Notes |
|---|---|---|
| Main Agent | The top-level Claude Code session running OMC | OMC's operating principles ("delegate specialized work", "verify before claiming") restate `Core/MAIN_AGENT_CONDUCT.md`'s No Direct Implementation and Verification Over Waiting in the runtime's own words. Where they differ, the framework's document wins. |
| Employee (42 + Domain Employees) | A `.claude/agents/*.md` agent | Generated by `Adapters/ai-runtimes/generate-agents.sh --target claude-code`. **OMC's built-in agents (`executor`, `architect`, `critic`, `verifier`, …) are tool labels, not Employees**: `Employee: executor` is refused by the `commit-msg` hook, and a dispatch to `executor` is a dispatch to nobody the framework can hold accountable. Dispatch to the generated Employee agent; OMC's agents may be *how* it runs, never *who* signs. |
| Employee Brief → Work Unit Report | The prompt to the agent → its return | OMC's "no fake completion" guard (placeholders, `test.skip`, `.only` are blockers) restates the Reporting Contract's "a bare Done is a failed Work Unit". The report format is still `Templates/WORK_UNIT_REPORT.md`; the runtime's guard does not replace it. |
| Director gate | `AskUserQuestion` | OMC routes clarification and approval through the same tool the framework's gates need. A gate is a *stop*: the session waits for the answer; it does not proceed on a default. |
| Dependent-task queue (`Core/ORCHESTRATION.md` Step 4) | `ultrawork` / `ralph` execution modes; OMC's task list | The modes give persistence and parallelism. The **layered termination** — Work Unit / Retry (two returns) / Queue / Blocked / Stopped — is the framework's and applies inside any mode. `ralph`'s "the boulder never stops" is a pacing statement; it does not override a `High`/`Critical` stop or a Director gate. |
| Conductor and poles (`Workflows/AUTONOMOUS_DELIVERY.md`) | `/team` — one orchestrating session dispatching worker sessions | The closest structural match. Each `/team` worker is a **pole**: it receives a `Templates/POLE_BRIEF.md`, runs on its own branch with disjoint write scope, and every control binds inside it. Escalation goes to the orchestrating session (the conductor), never to the user directly. The **integration pass** (Step 5) is not something `/team` performs; the conductor runs it explicitly. |
| Code Reviewer, Multi-Lens Review | `code-reviewer`, `security-reviewer`, `critic`, `verifier` agents | Usable as the *separate passes* of `Workflows/CODE_REVIEW.md`'s Multi-Lens Review, since they are separate agent invocations. Their findings are still consolidated into one Step 8 decision by the Code Reviewer Employee, and their decision block is recorded on the PR — the `Review Recorded` check reads the PR, not the runtime. |
| `SESSION_STATE.md` (dated operational state, never committed) | `.omc/notepad.md`, `.omc/project-memory.json`, `.omc/state/` | **Different things.** OMC's state is the third memory in `Templates/SESSION_STATE.md`'s table — runtime memory, machine-local, ignored (`.omc/` is in `.gitignore`). `SESSION_STATE.md` is the project's operational state, written for the *next Director*, not for the runtime. Do not let the runtime's notepad become the only place the project's state lives; do not copy `CLAUDE.md` into it (one fact, one place). |
| Risk Standard | — | No equivalent. `Standards/RISK_STANDARD.md` binds in full inside every OMC mode; a `High` action inside `autopilot` is a stop exactly as it is anywhere else. |
| Escape-hatch and suppression blocks | Claude Code hooks (`Adapters/ai-runtimes/claude-code/hooks/`) | OMC runs on Claude Code, so the hooks apply unchanged. OMC's own hooks inject `<system-reminder>` context; the framework's hooks refuse actions. They coexist in `.claude/settings.json`. |
| `Registry/` | `.omc/` | Unrelated. `Registry/` is derived, committed, machine-readable framework data. `.omc/` is runtime state. Neither reads the other. |

# What Is Not Mapped, and Why

- **OMC's model routing** (`haiku` / `sonnet` / `opus` per task size) is a runtime concern. The framework's `Core/CAPABILITY_TIERS.md` decides the *tier*; `generate-agents.sh --map` translates tiers to the runtime's capability names. Route by the Employee's tier, not by OMC's size heuristic, when they disagree.
- **OMC's keyword triggers** (`"ralph"`, `"ulw"`, `"autopilot"`) are conveniences of that runtime. No Workflow in this framework is triggered by them, and `Workflows/PROJECT_BOOTSTRAP.md`'s "project creation" phrase remains a documented convention rather than an OMC skill.
- **OMC's "Direct writes OK for `~/.claude/**`, `.omc/**`, `.claude/**`, `CLAUDE.md`, `AGENTS.md`"** is narrower than it reads under the framework: `CLAUDE.md` is the project's committed contract and changes to it are Work Units with a Director decision (`Workflows/ONBOARDING.md`); `.claude/settings.json` decides what the model may do and is reviewed like code (`Adapters/ai-runtimes/claude-code/hooks/README.md`). "Direct write" means without dispatch, not without review.
- **Team pipeline, commit protocol, and skills registry** of OMC are documented by OMC. Where OMC's commit protocol and `Standards/COMMIT_STANDARD.md` differ — trailer layout, one Work Unit per commit, the `Employee:` trailer — the Standard wins and the hooks enforce it.

# Adopting

1. Install the framework's Adapters (`Adapters/scripts/install.sh`) and the Claude Code hooks (`Adapters/ai-runtimes/claude-code/install-hooks.sh`). OMC's own setup is independent.
2. Generate the Employee agents: `./ia-engineering/Adapters/ai-runtimes/generate-agents.sh --target claude-code`. Dispatch to these, by Employee name.
3. When using `/team` for a mandate wider than one queue, run `Workflows/AUTONOMOUS_DELIVERY.md`: the orchestrating session is the conductor, each worker gets a Pole Brief, and the integration pass is run before delivery.
4. Record what turned out to be wrong in this mapping as a Work Unit against this file.
