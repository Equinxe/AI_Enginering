### Fixed

- `block-escape-hatches.sh` allows a `--get`, `--get-all` or `get` read of `core.hooksPath` in another command's arguments: `echo "$(git config --get core.hooksPath)"`, ``echo `git config --get core.hooksPath` `` and `printf '%s\n' "$(git config --get core.hooksPath)"` pass, up to 16 reads in one command segment. The read is exempt only where removing it hides nothing: the command holds no substitution inside another, an option's value holds no redirection, backtick or parenthesis, the read has no option that prints a key name or a value the command chooses (`--name-only`, `--get-regexp`, `--default`, `--file`, `--blob`), no option follows it, and the rest of its command names no git command and no `config`. A write stays refused: beside the read, in another substitution, joined across a substitution, as a `-c` option, or keyed by a read's output. A read in another git command's arguments is refused with a line that says to run it on its own. A legacy read in a substitution, ``echo `git config core.hooksPath` ``, stays refused, and its refusal now names the `--get` read to run. The hooks README's remedy for the refused legacy reads, to use `--get`, now holds for these forms (#272, WU-IAENG-455)
- `git commit-tree -p <parent>` is no longer refused as an interactive command. The interactive rule reads `rebase`, `add`, `commit`, `checkout` and `reset` only as whole command names, so `commit-tree`, `commit-graph` and `checkout-index` are other commands. `git commit -p`, `git-commit.exe -p` and a subcommand glued to an expansion that may be empty (`git commit$X -p`, `git rebase${X} -i`, `git reset"$x" --patch`) stay refused, and so does `git add--interactive --patch`, `git add -i`'s own helper where git still has it (#261, WU-IAENG-455)
- An `rm` of a path under `.git` with no `-r`, such as the stale `.git/index.lock` a session leaves behind, is still refused, but its reason no longer calls it a recursive removal. It names the path, and the remedy: wait until the session that holds the lock has finished, or ask a human to remove the lock by hand. A `-r` after `--` is a file name, so `rm -f .git/index.lock -- -r` gets that reason too. Whether to allow such an `rm` is a Director decision not yet taken (part of #235, WU-IAENG-455)
- A quoted message's last word after a `/` no longer reaches the rules. `strip-quotes.awk` keeps a dropped quoted region's last path component only when it names git, a dashed `git-<subcommand>`, `gh`, `rm` or `printf`, or when the region is glued to the text after it. So `git commit -m "docs: see Standards/core.hooksPath"` and `git commit -m "see docs/x--no-verify"` are allowed, and a quoted command path such as `"/c/Program Files/Git/cmd/git.exe"` is read as before (code review of PR #485, F3, WU-IAENG-455)
