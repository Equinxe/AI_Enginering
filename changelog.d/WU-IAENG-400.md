### Security

- Five Claude Code hooks no longer load files from the working directory when bash finds them through PATH (issue #344, SEC-IAENG-394-03). These are `block-escape-hatches.sh`, `block-inline-suppression.sh`, `post-edit-lint.sh`, `session-start.sh` and `stop-gate.sh`. They found their own directory with `dirname "$0"`, and when bash finds a hook through PATH, `$0` is the bare name. So a `lib.sh` in the working directory was sourced, and a `strip-quotes.awk` there was run as the escape-hatch lexer. A `context-alert.sh` there was run at session start. The suppression hook read its patterns from three levels above the working directory, and exempted the working directory's `tests/`. A cloned repository could plant any of these files. Each hook now takes its directory from `$0`, or from `BASH_SOURCE` only when `$0` is a bare name, cut at the last `/` or `\`. So a hook named by a Windows path is not exposed either, and a `BASH_SOURCE` set in the environment, which bash 5.3 imports, is not used for the installed absolute-path form. Running a hook as `bash <hook>.sh` through PATH remains unsupported, because a hook file of that name in the working directory runs instead. A hook that cannot load `lib.sh` behaves as before (issue #361 tracks the guards in that case). `hooks/tests/own-dir.sh` runs each hook from a working directory that holds a planted copy of every file it loads.
