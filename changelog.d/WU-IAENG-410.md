### Security

- The two guard hooks now fail closed when they fail, not only when they cannot read their input. `settings.example.json` gives `block-escape-hatches.sh` and `block-inline-suppression.sh` `"onFailure": "block"` and a 120 s `timeout`. A guard that hangs, cannot start, or exits with a code other than 0 or 2 now blocks the Bash call or the edit it guards (Claude Code 2.1.295 or later). Before, it had no timeout of its own: the 600 s default held the agent for ten minutes, and then the call went through unguarded. That happened once in production, on 27 October 2026, to an edit. 120 s is 1.25 times the slowest guard's worst p99 under load on Windows, so a healthy guard does not trip it. The Stop gate gets neither field: `onFailure` has no effect on Stop (#351, WU-IAENG-410)

### Added

- `Governance/BLOCKING_HOOK_LATENCY_MEASUREMENT.md`: how long the hooks take on Windows under parallel agents, from 1,490 production runs of the Stop gate, 758 paired Stop events and a 610-run bench that counts every process. Under load, a hook's latency is its process count: the Stop gate (29 processes) has a p95 of 16 s and a p99 of 26 s in production. `block-escape-hatches.sh` (84 processes per Bash call) has a modelled p50 of 9 s and a p99 of 61 s. The document also gives the 600 s default the issue had missed, the timeouts observed, and the mitigations ranked, with lightening `block-escape-hatches.sh` next (#385) (#351, WU-IAENG-410)
- `Adapters/ai-runtimes/claude-code/TROUBLESHOOTING.md` entry C: every Bash command or edit refused without an `iaeng: BLOCKED` reason, which is what a guard that cannot start now does, for example in a checkout whose framework submodule was never initialised (#351, WU-IAENG-410)

### Changed

- `stop-gate.sh` starts 4 commands instead of 8 on the path most stops take, a clean tree and a current `SESSION_STATE.md`. It reads the loop guard only before it blocks or reminds, runs `git rev-parse` only when `git status` fails, and reads the mtime, HEAD's time and the clock through new by-name forms of `lib.sh`'s helpers (`iaeng_file_mtime_to`, `iaeng_head_commit_time_to`, `iaeng_now_to`). These set a variable instead of printing one, and `iaeng_now_to` uses bash's own clock. The printing forms `session-start.sh` uses now wrap them. Benched under load against the earlier gate, it creates 15 processes per call instead of 29, and its p50 and p99 fall by 46 %. What it decides is unchanged. `hooks/tests/run.sh` checks that the loop guard still silences every block and reminder, that the gate says nothing outside a git directory, and that a pre-1970 mtime gives "could not determine" instead of a block. It holds the common path to its budget: `git` counted, no `jq`, at most 4 commands. A count of nothing now fails, where a stand-in directory under a drive-letter `TMPDIR` had passed with an empty log (#351, WU-IAENG-410)
- `check-framework-drift.sh`: for a hook entry whose script is missing, the report no longer says only that the check is silently gone. It also says that a guard whose entry has `"onFailure": "block"` now refuses every call it guards. `install-hooks.sh --check`'s summary says the installer updates an earlier framework entry in place, its matcher or the fields added since (#351, WU-IAENG-410)
- `install-hooks.sh` adds the two new fields in place to the framework's earlier guard entries, as it already updated an earlier matcher (WU-IAENG-373), instead of appending a second group that would run each guard twice per call. A guard entry with a field of its own, such as `"timeout": 1` or `"onFailure": "continue"`, is the project's: it is left as it is and reported as a near miss (#351, WU-IAENG-410)

The run prints `updated: PreToolUse [Bash]: block-escape-hatches.sh  (added: timeout, onFailure)` and the same for the edit guard. The file's `$comment` keeps its earlier text, because the merge never rewrites it; `--check` then reports the file as `customized`, which is expected (#351, WU-IAENG-410)
- **Minimum Claude Code: 2.1.295.** The guards fail closed only from that version on. An older version ignores `onFailure`: a guard that hangs or runs past 120 s lets the call through, sooner than the 600 s default did. Check with `claude --version` and update before you re-run the installer (#351, WU-IAENG-410)
- **Start Claude Code in the main checkout, not in a `git worktree` of it.** In a worktree whose framework submodule was never initialised, the guard scripts do not exist. A guard that cannot start now refuses the call, so every Bash command and every edit in that session is refused, with no message that names the cause (issue #394). If you must work there, run `git submodule update --init` in that worktree first. Subagents that Claude Code runs in worktrees are not affected: their hooks run from the main checkout (`Adapters/ai-runtimes/claude-code/TROUBLESHOOTING.md`, entry C) (#351, #394, WU-IAENG-410)
